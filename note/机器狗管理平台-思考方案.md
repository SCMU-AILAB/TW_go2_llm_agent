# 机器狗管理平台 · 思考方案

> 目标：做一个实验室多台机器狗的管理平台，先能看能管，后面能扩展成群控。
> 这一周交付：前端app做个demo
> 交付：技术栈 + 实现思路 + 前后端逻辑 + 连狗逻辑。

---

## 一、一句话说清

**一个 App，连到服务器；服务器管人和数据，再通过网络去指挥每只狗上的服务。**

```
App  →  服务器（Rust）  →  每只狗上的 FastAPI  →  SDK  →  狗本体
```

---

## 二、总体架构

```
┌──────────────────────┐
│      Flutter App      │  手机窄屏 / 电脑宽屏
│  列表 · 详情 · 我的    │
└──────────┬───────────┘
           │ HTTPS + Token
           ▼
┌──────────────────────────────────────┐
│           服务器（公网可访问）          │
│  ┌────────────────────────────────┐  │
│  │ Rust 业务服务                   │  │
│  │ 登录注册 · 用户 · 狗列表 · 日志   │  │
│  └───────────────┬────────────────┘  │
│  ┌───────────────▼────────────────┐  │
│  │ PostgreSQL：用户 / 狗 / 日志     │  │
│  └────────────────────────────────┘  │
└──────────────────┬───────────────────┘
                   │ HTTP（公网 / 内网均可）
                   ▼
┌──────────────────────────────────────┐
│        每条狗上：FastAPI 服务          │
│  负责狗与服务器之间的网络通信           │
│         │                             │
│  unitree_sdk2_bindings                │
│         │                             │
│        DDS（狗内部）                   │
└──────────────────┬───────────────────┘
                   ▼
              ┌─────────┐
              │  Go2 本体 │
              └─────────┘
```

**关键点**：
- **Rust 跑在服务器上**，管人、管数据、管权限。
- **FastAPI 跑在每条狗上**，负责狗和服务器的网络通信。
- **SDK 和 DDS 都在狗内部**，所以服务器不需要和狗在同一个网段，可以放公网。

---

## 三、各部分各干什么

| 部分 | 技术 | 放在哪 | 负责 |
|---|---|---|---|
| **前端** | Flutter | 用户手机 / 电脑 | 登录、狗列表、单狗详情、我的。宽屏两栏，窄屏分页 |
| **业务服务** | Rust + PostgreSQL | 服务器 | 登录注册、用户管理、狗列表、权限、操作日志 |
| **狗端服务** | FastAPI | **每条狗上** | 接收服务器的请求，调用 SDK 去读状态、发动作、抓图 |
| **底层** | unitree_sdk2_bindings + DDS | 狗内部 | 真正和机器狗通信 |

---

## 四、技术栈与选择理由

| 层 | 选择 | 为什么 | 替代方案 |
|---|---|---|---|
| 前端 | Flutter | 一套代码跑手机和电脑，宽窄屏自适应 | React Native、纯网页 |
| 业务后端 | Rust | 性能好、内存安全，组长推荐 | Python、Go |
| 狗端服务 | FastAPI | SDK 是 Python，天然对接；自带接口文档；跑在狗上，把 DDS 包成 HTTP | Flask |
| 数据库 | PostgreSQL | 用户、狗、日志是关系型数据，事务可靠 | SQLite、MySQL |
| 通信 | HTTP + 轮询 | 简单、够用，能跨公网 | WebSocket 推送 |
| 视频 | 截图 | 实现简单，一期够用 | 实时推流 |

**一句话**：一期优先保证"能跑通"，所以选实现成本低的方案；二期再上实时视频和推送。

## 五、前后端怎么运作（一次操作的完整过程）

**场景：登录 → 看狗 → 让狗站起来**

```
① 登录
   App → 服务器（Rust）：POST /api/auth/login
   Rust → 数据库：查用户、校验密码
   Rust → App：返回 token

② 看狗列表
   App → Rust：GET /api/dogs
   Rust → 数据库：查这个用户能看哪些狗
   Rust → App：返回列表

③ 列表每 2 秒刷新状态（轮询）
   App → Rust：GET /api/dogs/status
   Rust → 狗端 FastAPI：GET /state
   狗端 → SDK：读当前状态
   返回：在线/离线、电量、站/趴

④ 点某只狗，看详情
   App → Rust：GET /api/dogs/{id}
   Rust → 狗端 FastAPI：GET /{id}/detail
   狗端 → SDK：取状态 + 抓一张相机图
   返回：截图 + 电量 + 状态

⑤ 让狗站起来
   App → Rust：POST /api/dogs/{id}/command {"action":"stand_up"}
   Rust：查权限、写日志
   Rust → 狗端 FastAPI：POST /action
   狗端 → SDK：调 StandUp()
   返回：成功 / 失败
```

**为什么用轮询**：实现简单，先跑通。缺点是延迟 1~2 秒，二期可以换 WebSocket 推送。

## 六、连狗的逻辑

核心分两层：

```
服务器  ──HTTP──►  狗端 FastAPI  ──►  unitree_sdk2_bindings  ──►  DDS  ──►  狗
```

| 功能 | 怎么做 |
|---|---|
| **监测状态** | 狗端 FastAPI 持续读 SDK 的状态并缓存最新值；服务器来问时直接给缓存 |
| **下发指令** | 服务器发 HTTP 请求，狗端调 SDK 的动作接口：`StandUp` / `StandDown` / `StopMove` / `Move` |
| **截图** | 狗端调相机取帧，拿到一张 JPEG，返回给服务器，再给 App |

**关键点**：

1. **DDS 只在狗内部跑**，不跨网络。对外的只有 HTTP，所以服务器可以放公网。
2. **每条狗跑一个 FastAPI**，互不影响；加狗就是加一个服务。
3. **监测是"缓存最新值"**，不是每次去问狗。否则用户一多，狗会被问爆。

## 七、数据模型（最小三张表）

| 表 | 字段（大致） |
|---|---|
| `users` | id、用户名、密码哈希、角色、创建时间 |
| `dogs` | id、名字、序列号、访问地址、负责人、最后在线时间 |
| `logs` | id、用户、狗、动作、结果、时间 |

> 电量、站/趴这类**频繁变化的状态**，放内存缓存即可，不必写数据库。

---

## 八、接口清单（最小可跑）

| 方法 | 路径 | 作用 |
|---|---|---|
| POST | `/api/auth/register` | 注册 |
| POST | `/api/auth/login` | 登录，返回 token |
| GET | `/api/dogs` | 狗列表 |
| GET | `/api/dogs/status` | 批量状态（轮询用） |
| GET | `/api/dogs/{id}` | 单狗详情 |
| GET | `/api/dogs/{id}/snapshot` | 截图（JPEG） |
| POST | `/api/dogs/{id}/command` | 下发指令 |
| GET | `/api/logs` | 操作日志 |

## 十、风险和待确认

| # | 问题 | 影响 |
|---|---|---|
| 1 | **狗在内网，公网服务器怎么找到它？** | 两条路：狗主动连服务器（反向连接），或在实验室内做端口映射。没有这一步，"公网访问"落不了地 |
| 2 | **狗端服务的鉴权** | 狗端 FastAPI 暴露在网络上，必须有 token / 密钥，不能裸奔 |
| 3 | **多狗会不会冲突？** | 每条狗独立一个服务，理论上互不影响；但地址和端口要规划好 |
| 4 | **CPU 数据从哪来？** | SDK 不一定直接给 CPU 占用，可能要另想办法 |
| 5 | **Rust 的学习成本** | 三个人如果都不熟，一期可能被拖住 |

**建议**：这几条在方案里写"待确认"，比猜一个答案更专业。

---

## 十一、我们这个方案的特点

- **DDS 关在狗内部**：对外只露 HTTP，服务器放公网也没问题
- **加狗就是加服务**：每条狗一个 FastAPI，互不干扰
- **分层清楚**：App 只管界面，Rust 管人，狗端管狗，各不越界
- **先跑通，再优化**：轮询、截图，都是一期能立刻做出来的
- **诚实标注不确定**：公网怎么打通、鉴权、CPU 来源，都明确写"待确认"
